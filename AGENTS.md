# Правила работы над Tutor Platform

Последнее обновление контекста: 9 октября 2026 года.

## Главный приоритет

Экономно расходовать пятичасовой лимит, сохраняя качество результата. Выполнять только действия, которые непосредственно продвигают текущий этап разработки.

## Работа с контекстом

- В новом чате сначала прочитать этот файл, затем только разделы «Статус проекта» и «Следующий этап» в `README.md`.
- Перед любой задачей по API, авторизации, базе, миграциям, расписанию или списаниям дополнительно прочитать `docs/BACKEND_RULES.md` полностью.
- Перед изменением читать только файлы, относящиеся к текущей задаче.
- Сначала использовать `rg` и точечный просмотр нужных участков; не сканировать весь проект без причины.
- Не перечитывать уже изученные материалы в рамках одного этапа.
- Учитывать ранее принятые продуктовые решения и не задавать повторные вопросы.
- Не анализировать `components/ui/`, `dist/`, `.wrangler/`, `node_modules/` и сгенерированный `worker-configuration.d.ts`, если задача прямо их не касается.

## Быстрая карта проекта

- `components/tutor-app.tsx` — экраны преподавателя и ученика, формы и основные сценарии.
- `app/api/app-data/route.ts` — рабочий API, проверки доступа и операции с данными.
- `app/globals.css` — светлая и графитовая тёмная темы, включая календарь.
- `components/auth-gate.tsx` и `components/invite-accept.tsx` — вход и принятие приглашения.
- `db/schema.ts` — актуальная схема D1; `drizzle/` — последовательные миграции.
- `lib/lesson-maintenance.ts` — автоматическое списание завершённых уроков.
- `lib/telegram.ts` и `app/api/telegram/` — безопасная привязка Telegram и webhook бота.
- `workers/telegram-relay/` — минимальный внешний шлюз Telegram для недоступного с VPS `api.telegram.org`.
- `scripts/run-maintenance.mjs` — PostgreSQL worker: завершение уроков, напоминания и очередь Telegram.
- `worker-entry.ts` — Worker и фоновый запуск каждые 15 минут.
- `wrangler.deploy.jsonc` — рабочая конфигурация Cloudflare.
- `docs/BACKEND_RULES.md` — обязательные правила backend, ролей, базы и миграций.

## Текущее состояние

- Основной MVP развёрнут на VPS Selectel; рабочий домен: `https://tyuttori.ru`.
- Репозиторий: `https://github.com/iveivs/tutor-platform`, рабочая ветка развёртывания `migration/vps-postgres`.
- PostgreSQL отвечает за данные, собственные Argon2id-сессии — за авторизацию, Caddy — за HTTPS и reverse proxy.
- Реализованы роли, приглашения, ученики, постоянное и плавающее расписание, переносы, отмены, оплаты, отрицательный баланс, автоматическое списание, настройки профиля, адаптивность и две темы.
- Постоянное расписание создаёт уроки на 90 дней вперёд. Отменённые уроки сохраняются в истории; уникальный индекс запрещает активные дубликаты серии.
- Регистрация преподавателей закрыта: нового преподавателя приглашает только платформенный администратор персональной ссылкой. Для приглашённых кабинетов поддерживаются блокировка, бессрочный бесплатный доступ и подтверждаемое окончательное удаление.
- Юридические документы редакции 1.0 опубликованы в `/legal`; HTML и PDF читаются во время выполнения из исключённой из Git папки `private/legal-documents`, принятие обязательных документов отдельно подтверждается и журналируется в `legal_acceptances`.
- Фотографии и файлы пока не загружаются. Внешнее S3-хранилище и внешний backup ещё не подключены; до этого перед развёртыванием нужен отдельный `pg_dump` на сервере.
- Почтовый домен `tyuttori.ru` подтверждён в Selectel; SPF, DKIM и DMARC настроены. SMTP работает через TLS-порт 1127, секрет находится только в серверном `.env`.
- Telegram-модуль активирован в production: бот `@tyuttori_bot`, одноразовая привязка, очередь с повторами, изменения расписания, запросы учеников и одно напоминание за 24 часа. Прямой доступ Selectel VPS к `api.telegram.org` недоступен, поэтому webhook и исходящие Bot API-запросы проходят через защищённый Cloudflare relay; токен бота хранится только как secret relay.

## Уведомления

- Не отправлять внешнее сообщение прямо из операции расписания: сначала фиксировать предметное изменение и очередь в той же транзакции.
- Telegram разрешён только для напоминания за 24 часа, изменения расписания ученика и нового запроса ученика преподавателю.
- Внутренние `notifications` и предметные таблицы остаются источником истины; Telegram — добровольный дополнительный канал.
- `chat_id`, токен бота, webhook-secret, relay-secret и SMTP-пароль не выводить в логи и не добавлять в Git.
- Relay принимает только `sendMessage`, `getMe`, `getWebhookInfo` и безопасно переопределяемый `setWebhook`; не превращать его в общий прокси Telegram API.
- При изменении типов внешних уведомлений синхронно проверить PostgreSQL-триггер в новой миграции и worker-доставку.

## Изменения

- Сохранять текущий стек, архитектуру, дизайн и пользовательские данные.
- Никогда не удалять, не скрывать, не переименовывать и не заменять уже существующую пользовательскую функцию без прямой просьбы пользователя. Если новая задача конфликтует с прежним сценарием, сохранить оба сценария или сначала запросить решение.
- Объединять связанные изменения в один содержательный патч.
- Не выполнять рефакторинг, обновление зависимостей или косметическую переработку вне текущего этапа.
- Не создавать временные версии, дубли файлов и альтернативные реализации без необходимости.
- Для редактирования файлов использовать `apply_patch`.

## Агенты и инструменты

- Не запускать дополнительных агентов, если пользователь прямо этого не попросил.
- Не использовать интернет, генерацию изображений и внешние сервисы без необходимости или прямой просьбы.
- Объединять независимые чтения и проверки в минимальное количество вызовов инструментов.
- Не повторять успешный вызов инструмента, если исходные данные не изменились.

## Проверка результата

- Во время реализации использовать самые узкие релевантные проверки.
- После завершения этапа выполнить одну итоговую сборку.
- Запускать линтер или дополнительные тесты только при изменениях, которые они действительно проверяют, либо по просьбе пользователя.
- Не проводить повторную визуальную проверку неизменённых экранов.
- Локальный сервер переиспользовать, а не запускать дубликаты.
- Для интерфейсных изменений достаточно одной сборки и проверки затронутого сценария; полный аудит проводить только по отдельной просьбе.

## Общение

- Давать не более одного короткого сообщения о начале этапа и одного сообщения о результате.
- Не перечислять внутренние команды и технические подробности, если пользователь их не запрашивал.
- Если для продолжения нужны ключи, разрешение или решение пользователя, задать один конкретный вопрос.

## Команды и публикация

- Локальная проверка: `npm run build`, затем `npm run start`; адрес `http://127.0.0.1:8787`.
- Разработка с обновлением: `npm run dev`; адрес `http://localhost:5173`.
- Перед публикацией проверить `git diff --check` и выполнить одну итоговую сборку.
- Миграции рабочей PostgreSQL-базы применять только при появлении нового неприменённого файла в `drizzle-postgres/`; старые файлы не редактировать после применения.
- Секреты находятся только в `.env.local`; не читать их содержимое без необходимости и никогда не выводить или добавлять в Git.
- Полные команды публикации и настройки находятся в `README.md`; не искать их заново в интернете.
