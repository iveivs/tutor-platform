# Tutor Platform

Веб-приложение для частных преподавателей и их учеников. Первый пользователь продукта — преподаватель барабанов, но архитектура рассчитана на дальнейшее подключение других репетиторов и переход к подписной SaaS-модели.

Проект находится в активной разработке. Основной контур публикуется на VPS Selectel по адресу [tyuttori.ru](https://tyuttori.ru) и использует PostgreSQL и собственную Argon2id-авторизацию. Прежний Cloudflare-контур сохранён на время контролируемого перехода; порядок проверок и отката описан в [`docs/VPS_MIGRATION.md`](docs/VPS_MIGRATION.md).

## Что уже работает

### Кабинет преподавателя

- обзор занятий на выбранный день;
- календарь в режимах дня, недели и месяца;
- список учеников с поиском и фильтрами;
- постоянное и плавающее расписание;
- автоматическое создание конкретных уроков из постоянного расписания на 90 дней вперёд;
- карточка ученика;
- баланс оплаченных занятий, включая отрицательные значения;
- добавление ученика, урока и оплаты;
- бесплатные пробные занятия для новых посетителей без засорения списка учеников;
- архивирование, восстановление и подтверждаемое окончательное удаление учеников;
- запросы на перенос, отмену и создание нового занятия;
- подтверждение и отклонение запросов;
- светлая и тёмная тема с сохранением выбора;
- рабочие настройки профиля с изменением имени преподавателя;
- закрытое приглашение новых преподавателей платформенным администратором;
- блокировка и подтверждаемое удаление кабинетов преподавателей;
- адаптивный интерфейс для компьютера и телефона.

### Кабинет ученика

- персональный вход по приглашению;
- автоматическое продление безопасной сессии без повторного входа каждый час;
- ближайший урок, баланс и история оплат;
- запрос переноса или отмены ближайшего урока;
- предложение даты и времени нового урока при плавающем расписании;
- уведомления о решении преподавателя и отрицательном балансе.

## Основные правила продукта

- Оплата может быть разовой или абонементом на несколько занятий.
- Баланс хранится в занятиях и может становиться отрицательным.
- После окончания проведённого урока должно автоматически списываться одно занятие.
- Если ученик не пришёл, урок всё равно считается проведённым.
- Ученик не изменяет расписание напрямую: он отправляет запрос преподавателю.
- Запрос отмены можно отправить не позднее 23:59 дня, предшествующего уроку.
- Если отмена запрошена вовремя, но преподаватель ещё не ответил, занятие не должно списываться.
- При переносе ученик может предложить новое время, окончательное решение принимает преподаватель.
- Для плавающего расписания ученик может предложить новый урок, но преподаватель должен его подтвердить.
- Двойной урок создаётся как два связанных последовательных занятия: переносится и отменяется целиком, а после проведения списывает два занятия.
- В интерфейсе ученика показывается количество занятий на балансе и отдельная история оплат.

  schema.ts           схема базы данных

Клиентский интерфейс обращается к `/api/app-data`. API выполняет проверку входных данных и работает с базой через подготовленные запросы. Все рабочие записи принадлежат отдельному `workspace`, поэтому данные разных преподавателей можно изолировать без изменения основной модели.

## Структура данных

К рабочим таблицам добавлены отдельные таблицы регистрации и платформенного аудита:

| Таблица | Назначение |
| --- | --- |
| `workspaces` | независимые кабинеты преподавателей или будущих школ |
| `users` | учётные записи системы авторизации без хранения паролей |
| `members` | преподаватели и ученики внутри кабинета |
| `lesson_series` | шаблоны постоянного еженедельного расписания |
| `lessons` | конкретные занятия с датой и временем |
| `lesson_events` | неизменяемая история назначения, переноса, отмены и проведения уроков |
| `balance_entries` | оплаты, списания, возвраты и корректировки баланса |
| `lesson_requests` | запросы на отмену, перенос или новый урок |
| `invitations` | безопасные одноразовые приглашения учеников |
| `notifications` | внутренние уведомления преподавателей и учеников |
| `data_changes` | адресный технический журнал для частичной синхронизации открытых кабинетов |
| `teacher_registrations` | ожидающие подтверждения регистрации преподавателей; паролей здесь нет |
| `platform_audit_events` | неизменяемый журнал блокировок и разблокировок кабинетов |
| `legal_acceptances` | неизменяемый журнал принятия юридических документов с версией, временем и источником |

Баланс не хранится одним изменяемым числом. Он вычисляется как сумма операций: оплата добавляет занятия, проведённый урок списывает одно. Ошибочная оплата отменяется отдельной связанной обратной операцией: исходная запись остаётся в истории, а повторная отмена блокируется базой данных.

Подробнее правила модели описаны в [`db/README.md`](db/README.md).
Обязательные серверные инварианты, роли, жизненный цикл уроков, списания и правила миграций собраны в [`docs/BACKEND_RULES.md`](docs/BACKEND_RULES.md).

## Локальный запуск

### Требования

- Node.js 22.13 или новее;
- npm;
- Git.

### 1. Установка

```bash
npm ci
```

### 2. Сборка конфигурации

```bash
npm run build
```

### 3. Применение миграции к локальной базе

```bash
node --import ./scripts/sites-env.mjs ./node_modules/wrangler/bin/wrangler.js d1 execute DB \
  --local \
  --config dist/server/wrangler.json \
  --persist-to .wrangler/state \
  --file drizzle/0000_silent_hellcat.sql
```

Миграцию нужно применять один раз к новой локальной базе.

### 4. Добавление демонстрационных данных

```bash
node --import ./scripts/sites-env.mjs ./node_modules/wrangler/bin/wrangler.js d1 execute DB \
  --local \
  --config dist/server/wrangler.json \
  --persist-to .wrangler/state \
  --file db/seed.local.sql
```

Скрипт безопасно запускать повторно: существующие демонстрационные записи не дублируются.

### 5. Запуск приложения

```bash
npm run dev
```

После запуска приложение доступно по адресу [http://localhost:5173](http://localhost:5173).

Локальные команды разработки явно включают демонстрационный режим только для loopback-адресов. Если Supabase не настроен в опубликованной версии, рабочий API закрывается с ошибкой `503`, а не предоставляет демонстрационный доступ.

## Работа с миграциями

1. Изменить `db/schema.ts`.
2. Выполнить `npm run db:generate`.
3. Проверить созданный SQL-файл.
4. Применить только новую миграцию к локальной базе.
5. Не изменять миграции, которые уже применялись на сервере.

Демонстрационные данные не входят в миграции и хранятся отдельно в `db/seed.local.sql`.

## Безопасность

- Пароли не хранятся в базе приложения.
- Токен восстановления приходит во фрагменте ссылки, немедленно удаляется из адресной строки и передаётся только собственному API для установки нового пароля.
- Токены приглашений должны сохраняться только в виде криптографического хеша.
- Доступ к данным должен проверяться на сервере по пользователю и кабинету.
- Каждый API-запрос ограничен кабинетом вошедшего пользователя; данные разных преподавателей не смешиваются.
- Роль администратора платформы не расширяет `/api/app-data`: администратор видит только метаданные кабинета и журнал административных действий.
- Заблокированный кабинет закрывается для всех его memberships при каждой серверной проверке сессии; данные при этом не удаляются.
- Короткоживущий токен доступа и токен продления хранятся только в защищённых `HttpOnly` cookie.
- Клиентские идентификаторы нельзя использовать как доказательство прав доступа.
- Локальные файлы окружения, база, сборка и зависимости исключены из Git.

## Настройка авторизации

Авторизация использует Supabase Auth на бесплатном тарифе, а рабочие данные остаются в D1. Это разделяет вход пользователей и предметные данные приложения, не привязывая расписание к одному поставщику авторизации.

1. Создайте бесплатный проект в Supabase.
2. В разделе API Keys скопируйте URL проекта и `Publishable key`.
3. Там же скопируйте серверный `Secret key`. Не публикуйте его и не добавляйте в GitHub.
4. Скопируйте `.env.example` в `.env.local` и заполните значения Supabase и `PUBLIC_APP_URL`.
5. Перезапустите локальное приложение.
6. Укажите email первого преподавателя в `INITIAL_OWNER_EMAIL`, а отображаемое имя — в `INITIAL_OWNER_NAME`.
7. Создайте пользователя с этим email в Supabase Auth. При первом успешном входе приложение автоматически создаст для него кабинет преподавателя в пустой базе D1.
8. Включите в Supabase обязательное подтверждение email, добавьте `PUBLIC_APP_URL` в разрешённые Redirect URLs и настройте SMTP для рабочих писем.
9. Для отдельного администратора платформы укажите его заранее созданный Supabase email в `PLATFORM_ADMIN_EMAIL`. Первый владелец существующего кабинета сохраняет административный доступ после миграции для обратной совместимости.

Приложение также понимает прежние переменные `SUPABASE_ANON_KEY` и `SUPABASE_SERVICE_ROLE_KEY`, но для новых проектов используются актуальные `SUPABASE_PUBLISHABLE_KEY` и `SUPABASE_SECRET_KEY`.

После настройки вход станет обязательным. В карточке нового ученика нажмите «Пригласить ученика»: приложение покажет персональную ссылку, которую можно отправить через системное меню или скопировать вручную. Ученик открывает её, задаёт личный пароль и получает доступ только к своему кабинету.

Открытая регистрация преподавателей отключена. Новый кабинет создаётся только по персональной ссылке, которую платформенный администратор выпускает для конкретных имени и email. Преподаватель открывает ссылку, задаёт пароль и получает независимый `workspace`. Ссылка одноразовая, действует 14 дней, а в D1 хранится только её SHA-256-хеш.

При принятии приглашения пользователь отдельно подтверждает Пользовательское соглашение и согласие на обработку персональных данных. Для несовершеннолетнего приглашение принимает законный представитель с дополнительным подтверждением. Сервер сохраняет тип и редакцию документа, время, роль участника, источник и сведения браузера в `legal_acceptances`. Публичные документы доступны в разделе [`/legal`](https://tyuttori.ru/legal), а на странице каждого документа доступна PDF-версия.

Заполненные юридические оригиналы хранятся локально в `private/legal-documents/`, исключены из Git и из контекста сборки Docker. На VPS эта папка монтируется в контейнер только для чтения. Для рабочего запуска в ней должны находиться пять Markdown-файлов и соответствующие PDF; редактируемые DOCX можно хранить рядом как локальный архив.

Админка доступна из настроек владельца-администратора или отдельному аккаунту из `PLATFORM_ADMIN_EMAIL`. Она показывает владельца, дату создания, последнюю активность, статус и число учеников, позволяет приглашать преподавателей, блокировать/разблокировать кабинет и сохраняет изменения доступа в журнале. Приглашённым сейчас выдаётся бессрочный бесплатный доступ; поля модели отдельно сохраняют способ и срок доступа для будущих пробных периодов и платных тарифов. Окончательное удаление возможно только после блокировки и повторного ввода email преподавателя. Пароли, уроки, оплаты и содержимое кабинета через административный API не выдаются.

На экране входа доступно восстановление пароля по email. Supabase отправляет письмо со ссылкой, после которой пользователь задаёт новый пароль в приложении. Ответ формы не сообщает, зарегистрирован ли введённый адрес. Для рабочего использования настройте собственный SMTP в Supabase: встроенная почтовая отправка предназначена для тестирования и имеет строгие ограничения частоты.

## Размещение в Cloudflare

Рабочая конфигурация хранится в `wrangler.deploy.jsonc`. Секреты не входят в репозиторий и передаются Cloudflare из локального `.env.local` только во время публикации.

```bash
npm run build
npx wrangler d1 migrations apply tutor-platform-db --remote --config wrangler.deploy.jsonc
npx wrangler deploy --config wrangler.deploy.jsonc --secrets-file .env.local
```

Миграцию нужно применять после появления новых файлов в `drizzle/`. Обычное обновление интерфейса достаточно собрать и опубликовать последней командой. Развёрнутая версия работает в аккаунтах Cloudflare и Supabase владельца и не зависит от подписки ChatGPT или хостинга Sites.

Cloudflare запускает фоновую обработку каждые 15 минут. Она списывает завершённые уроки даже тогда, когда преподаватель и ученики не открывают приложение. Своевременный необработанный запрос отмены по-прежнему блокирует списание.

Раздел «История» объединяет события уроков, операции баланса и запросы учеников. Преподаватель может фильтровать ленту по ученику и типу события, а ученик видит только собственную историю. Переносы сохраняют прежнее и новое время.

Открытый кабинет автоматически синхронизируется без перезагрузки страницы. С 07:00 до 01:00 по Москве лёгкая проверка выполняется раз в минуту, с 01:00 до 07:00 — раз в 10 минут; при возвращении на вкладку или восстановлении интернета проверка выполняется сразу. Сервер сначала читает адресный журнал изменений и загружает только изменившиеся разделы — например, запросы и уведомления, не затрагивая оплаты и всю историю.

## Статус проекта

Основной MVP работает на VPS Selectel с PostgreSQL, собственной авторизацией, Caddy и Docker Compose. Рабочий домен — `tyuttori.ru`. Регистрация преподавателей закрыта и доступна только по приглашению администратора; ученики подключаются по приглашению преподавателя.

На сайте опубликованы юридические документы редакции 1.0 от 6 октября 2026 года. В формах принятия приглашений обязательные согласия разделены, не отмечены заранее и журналируются в базе. Фотографии и пользовательские файлы пока не загружаются; внешнее S3-хранилище и рабочий внешний backup ещё требуется подключить.

Последние завершённые изменения:

- имя и фамилия ученика разделены, email остаётся необязательным;
- данные ученика можно исправить из его карточки;
- постоянное расписание можно задать сразу при создании ученика;
- у выбора времени появились кнопки изменения на час;
- перенос изменяет исходный урок, удаление действительно убирает его из расписания;
- генерация постоянного расписания защищена от активных дубликатов;
- тёмная тема стала нейтрально-графитовой, поле календаря отделено от фона, выходные выделены сильнее.

## Как продолжить в новом чате

Откройте рабочую папку `Sites/tutor-platform` и сформулируйте конкретную следующую задачу. Достаточно написать: «Прочитай `AGENTS.md` и разделы “Статус проекта” и “Следующий этап” в `README.md`, затем займись …». Полностью пересказывать историю разработки или прикладывать старую переписку не требуется.
