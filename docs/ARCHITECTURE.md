# Архитектура Tutor Platform

Этот документ — карта проекта для разработчика, который впервые открывает репозиторий. Он описывает размещение кода и границы модулей. Бизнес-инварианты находятся в [`BACKEND_RULES.md`](BACKEND_RULES.md), правила интерфейса — в [`FRONTEND_ARCHITECTURE.md`](FRONTEND_ARCHITECTURE.md).

## Рабочий контур

Production работает как Next.js standalone на VPS Selectel за Caddy. Предметные данные и серверные сессии находятся в PostgreSQL. Отдельный worker выполняет периодические задания. Закрытые фотографии и документы хранятся в Selectel S3.

Cloudflare/D1 и Supabase оставлены только как совместимый старый контур. Переменная `TUTOR_RUNTIME_TARGET=node` включает PostgreSQL-адаптеры через aliases в `next.config.ts`. Новая production-логика не должна создавать записи в старом контуре.

## Слои проекта

```text
app/                                  страницы и HTTP-маршруты Next.js
  api/                                тонкий транспортный слой API
components/
  ui/                                 базовые shadcn/Radix-примитивы
  common/                             общие составные блоки приложения
  features/<feature>/                 интерфейс и клиентская логика функции
  features/activity/                  запросы, уведомления и история преподавателя
lib/
  app-data/                            чтение и команды основного кабинета
  lesson-content/                     заметки, домашние задания и материалы урока
  teacher-material-library/           библиотека PDF/Word/изображений преподавателя
  account-endpoints/                  приглашения и восстановление пароля
  admin-workspaces/                   операции платформенной админки
  node-auth/                           cookie, криптография и PostgreSQL-сессии

```

## Поток запроса

```text
route.ts
  → проверка транспорта: origin, сессия, rate limit, размер и схема тела
  → предметный handler/action
  → параметризованный запрос или транзакция PostgreSQL
  → безопасный DTO/Response без внутренних полей базы
```

`route.ts` не содержит объёмную бизнес-логику. Он экспортирует обработчики из предметного модуля либо выполняет только короткую совместимую развилку между старым и Node-контуром.

Изменяющая операция повторно проверяет роль и `workspace_id`. Связанные записи выполняются одной транзакцией. Клиентский идентификатор никогда не считается подтверждением доступа.

## Основные предметные модули

### Кабинет

`lib/app-data/read-handler.ts` собирает разрешённые разделы кабинета. `write-handler.ts` отвечает за транспортные проверки, а `write-actions.ts` маршрутизирует команды в модули профиля, учеников, уроков, баланса, запросов и групп.

### События преподавателя

`components/features/activity/` объединяет активные запросы, внутренние уведомления и историю, не смешивая их источники истины. Уведомления получают идентификаторы связанных ученика, запроса и урока из DTO кабинета: сообщение открывает нужную переписку, а ожидающий запрос — соответствующую карточку с действиями. Открытие источника помечает прочитанным только выбранное уведомление; массовое действие остаётся отдельной командой.

### Материалы урока

`lib/lesson-content/` содержит схему действий, чтение и выполнение операций с заметками, домашними заданиями, фотографиями и назначенными документами. Библиотека преподавателя находится отдельно в `lib/teacher-material-library/`; загрузка, замена, метаданные и удаление имеют самостоятельные handlers.

### Групповые занятия

Группа (`student_groups`, состав, недельные слоты) создаёт по строке `lessons` на каждого участника с общим `class_id`, поэтому баланс, списания и отмены работают как у индивидуальных уроков. Команды — `lib/app-data/write-group-actions.ts`, генерация по слотам — `ensureSeriesLessons` в `lib/app-data/route-utils.ts`, склейка строк в одно занятие для экрана — `lib/group-sessions.ts`, экраны — `components/features/groups/`. Материалы преподавателя хранятся на одной «якорной» строке занятия и видны всем участникам (`resolveLessonAccess`, `sessionLessonIds`, `studentSeesLessonSql` в `lib/lesson-materials.ts`). Статистика (`lib/teacher-stats.ts`) и сводка в Telegram (`scripts/run-maintenance.mjs`) считают занятие один раз. Подробные правила — раздел «Групповые занятия» в `docs/BACKEND_RULES.md`.

### Статистика

`GET /api/teacher-stats` и `lib/teacher-stats.ts` считают показатели преподавателя за период на сервере; экран — `components/features/stats/stats-view.tsx`.

### Авторизация и аккаунты

`lib/node-auth/core.ts` содержит криптографию, cookie и безопасные вспомогательные функции. `sessions.ts` работает с PostgreSQL-сессиями и участниками кабинета. Публичные приглашения и восстановление пароля разделены в `lib/account-endpoints/`. Файлы `lib/node-auth.ts` и `lib/postgres-account-endpoints.ts` — стабильные фасады для существующих imports и runtime aliases.

### Администрирование

`lib/admin-workspaces/` изолирует проверку платформенного администратора, чтение метаданных кабинетов и изменяющие операции. Платформенный администратор не получает доступ к предметным данным чужого кабинета.

## Правила зависимостей

- `components/ui` не импортирует feature-компоненты или предметные API.
- `components/common` не содержит бизнес-правила конкретной функции.
- feature-компонент может использовать `ui`, `common` и собственные `api.ts`/типы.
- `app/api/**/route.ts` делегирует работу в `lib`, когда обработчик перестаёт быть коротким.
- предметный модуль не импортирует React-компоненты.
- общий код выносится только после появления второго реального потребителя; абстракции «на будущее» не создаются.
- production-запросы к базе параметризованы и всегда ограничены `workspace_id`, когда работают с данными кабинета.

Ориентиры, а не жёсткие лимиты: компонент свыше 250 строк и API/handler свыше 300 строк требуют проверки на смешение обязанностей. Разделение выполняется по предметному смыслу, а не на произвольные куски одинакового размера.

## Как добавить функцию

1. Определить feature и проверить существующие компоненты в `components/ui`, `components/common` и `components/features`.
2. Добавить или расширить серверную схему входных данных; принимать только известные поля.
3. Поместить бизнес-операцию в соответствующий модуль `lib`, сохранив проверки роли, `workspace_id`, rate limit и транзакции.
4. Добавить русский и английский варианты каждого видимого текста, включая ошибки, пустые и загрузочные состояния.
5. При изменении схемы создать новую добавочную миграцию; применённые миграции не редактировать.
6. Добавить релевантные тесты и выполнить типизацию, линтер, тесты и production-сборку.
7. Для production проверить readiness и только безопасные сценарии; операции с реальными данными выполнять по отдельному плану.

## Проверки перед публикацией

```bash
npx tsc --noEmit
npm run lint
npm test
npm run build
git diff --check
```

После развёртывания проверяются `/api/health/live`, `/api/health/ready`, состояние контейнеров и отсутствие новых ошибок в логах. Для миграций, backup и отката используется [`VPS_OPERATIONS.md`](VPS_OPERATIONS.md).
