# Правила backend и базы данных

Этот файл — источник обязательных серверных инвариантов. Перед изменением API, авторизации, фоновой обработки, схемы или миграций нужно читать его вместе с релевантным кодом. Интерфейс не должен обходить эти правила.

## Границы систем

- Основной рабочий контур запускается на VPS Selectel: Next.js standalone, PostgreSQL, собственная авторизация и Caddy. Cloudflare Worker, D1 и Supabase Auth сохранены только как прежний контур и не получают новые рабочие записи.
- PostgreSQL хранит кабинеты, пользователей, Argon2id-хеши паролей, сессии, роли, учеников, расписание, запросы, баланс, приглашения и уведомления.
- Отдельный Node-процесс каждые 15 минут запускает обработку завершённых уроков.
- Секретные ключи доступны только серверу через переменные окружения. В Git разрешены только имена переменных; production-секреты и пароли туда не попадают.

### Целевой контур после переключения

- Приложение запускается как Next.js standalone на Node.js за Caddy; PostgreSQL является единственным источником предметных данных.
- Пароли хешируются Argon2id и никогда не сохраняются или не журналируются в открытом виде. Серверная сессия хранится в PostgreSQL только в виде хеша непрозрачного токена; cookie имеет `HttpOnly`, `Secure` и `SameSite=Lax`.
- Node-авторизация закрывается с `503`, если отсутствует `DATABASE_URL` или `AUTH_SECRET` длиной не менее 32 символов. Обновление сессии атомарно отзывает старый токен, выход отзывает текущий, а заблокированный кабинет не может продолжить ранее созданную сессию.
- Журнал авторизации не хранит исходные email и IP: для корреляции используются HMAC-SHA-256 с `AUTH_SECRET`. Отдельный платформенный администратор сохраняет вход в админку при блокировке собственного кабинета, но не получает через это доступ к предметным данным заблокированного кабинета.
- Изменяющие запросы сохраняют текущие проверки origin, схемы входных данных, роли и `workspace_id`. Ограничение частоты переносится в PostgreSQL и должно быть атомарным между экземплярами приложения.
- Фоновая обработка запускается отдельным процессом с PostgreSQL advisory lock, поэтому одновременно работает не более одного обработчика каждого задания.
- Публичные auth-маршруты и запросы ученика ограничены 10 обращениями в минуту, остальные изменяющие API-запросы — 60 обращениями в минуту. Счётчики PostgreSQL обновляются атомарно, а их ключи сохраняются только как HMAC-хеши.
- Токены приглашений действуют 14 дней, токены установки и восстановления пароля — один час. В PostgreSQL хранится только SHA-256-хеш; новый токен отзывает предыдущие неиспользованные токены того же назначения, успешная смена пароля отзывает все активные сессии пользователя.
- SMTP-секреты задаются только через окружение. Ошибка доставки не раскрывает существование аккаунта и не выводит email или содержимое письма в журнал.
- До удаления старого контура хранится полный D1-экспорт. Откат приложения после появления новых записей в PostgreSQL выполняется на предыдущую версию Node-приложения с той же PostgreSQL-базой; простое возвращение DNS на D1 запрещено из-за потери новых данных.
- Исторические данные D1 объединены с действующей PostgreSQL 10 октября 2026 года: совпавшие пользователи и участники сопоставлены по нормализованному email, а уже созданные Argon2id-пароли, сессии и новые предметные записи сохранены. Исторические уведомления переносились с выключенными триггерами внешней доставки и не создавали Telegram-сообщения.
- Один закрытый Selectel S3 может использовать раздельные префиксы для фотографий уроков и зашифрованных PostgreSQL-backup. Права ключа и префиксы должны быть минимально необходимыми; готовность backup подтверждается только успешным снимком и проверкой восстановления.
- Рабочий PostgreSQL не публикуется наружу. Production-секреты не находятся в Git и хранятся отдельно от зашифрованных резервных копий; потеря `RESTIC_PASSWORD` недопустима.

## Авторизация, роли и изоляция данных

- Каждый рабочий запрос сначала определяет пользователя по собственной серверной сессии PostgreSQL, активного `member`, его роль и `workspace_id`.
- Все чтения и изменения предметных данных обязательно ограничиваются `workspace_id`; идентификатор из клиента не является доказательством доступа.
- `owner` и `teacher` управляют учениками, уроками, сериями, оплатами и решениями по запросам.
- `student` читает только собственные уроки, баланс, оплаты, запросы и уведомления. Он может создавать только собственные запросы и отмечать собственные уведомления прочитанными.
- `platform_admin` проверяется отдельно от membership. Эта роль может читать только метаданные кабинетов и административный журнал, а также менять `workspaces.access_status`; она не обходит ограничения `/api/app-data` и не даёт доступ к предметным данным чужого кабинета.
- `workspaces.access_status = blocked` закрывает вход и каждую серверную сессию всех участников кабинета. Блокировка не удаляет и не изменяет предметные данные.
- Запросы изменения состояния принимаются только с того же origin и проходят серверную проверку входных данных.
- Отсутствие `DATABASE_URL` или достаточно длинного `AUTH_SECRET` закрывает рабочий API с ошибкой `503`. Демонстрационный режим включается только локальными командами разработки и дополнительно ограничен адресами `localhost`, `127.0.0.1` и `::1`.

## Регистрация преподавателей и администрирование

- Открытая регистрация преподавателей отключена. Новый кабинет может создать только платформенный администратор через персональное приглашение на заранее указанный нормализованный email.
- В PostgreSQL хранится только SHA-256-хеш токена приглашения. Ссылка одноразовая, действует 14 дней и после принятия связывается с созданным кабинетом.
- Пароль хешируется Argon2id на сервере. Новый преподаватель получает отдельные `users`, `workspaces` и owner membership одной транзакцией PostgreSQL.
- Приглашённый кабинет сейчас получает `access_grant = complimentary` без срока окончания. Поля `access_grant` и `access_expires_at` зарезервированы для будущих пробных периодов и платного доступа.
- Отдельного платформенного администратора можно bootstrap-ить только через серверную переменную `PLATFORM_ADMIN_EMAIL`; существующий первый владелец получает роль миграцией для обратной совместимости. Флаг хранится в D1 и никогда не принимается от клиента.
- Блокировка и разблокировка кабинета выполняются атомарно вместе с добавлением `platform_audit_event`. Административный API не возвращает расписание, оплаты, запросы или уведомления кабинета.
- Окончательное удаление кабинета доступно только после блокировки, запрещено для кабинета администратора и требует точного повторного ввода email владельца. Удаление очищает связанные рабочие данные и локальную учётную запись PostgreSQL.

## Ученики и приглашения

- Пользовательское соглашение, правила пользовательского контента и согласие на обработку персональных данных принимаются отдельными, не отмеченными заранее чекбоксами. Для несовершеннолетнего форму заполняет законный представитель и отдельно подтверждает своё полномочие.
- Каждое принятие сохраняется неизменяемой записью `legal_acceptances`: пользователь, кабинет и участник, тип и версия документа, источник, статус участника, время и сокращённый User-Agent. Клиентские флаги не считаются доказательством без серверной проверки буквального значения `true`.
- Изменение текста юридического документа требует новой версии; прежние записи принятия не обновляются и не удаляются.

## Заметки, фотографии и документы урока

- Ученик и преподаватель имеют по одной общей редактируемой заметке к уроку; преподаватель дополнительно имеет личную заметку, недоступную ученику. Заметки ограничены 4000 символами и не удаляются автоматически.
- Автор может редактировать и удалять свою заметку. Преподаватель может удалить общий материал ученика в пределах своего `workspace`; личную заметку другого преподавателя он не видит.
- Перед первой записью пользователь должен принять актуальную редакцию `content_rules`. Новое принятие сохраняется в `legal_acceptances` с источником `in_app`; старые принятия не перезаписываются.
- На одного участника и урок разрешено не более пяти активных фотографий. Исходный файл ограничен 5 МБ, декодируется сервером, поворачивается, уменьшается до 2000×2000, преобразуется в WebP и сохраняется без исходных EXIF-метаданных.
- Фотографии находятся только в закрытом S3-префиксе. API проверяет сессию, `workspace_id` и принадлежность урока ученику; постоянных публичных URL нет.
- Фотография получает срок `ends_at` урока плюс 90 дней. После срока либо явного удаления она исчезает из API, а worker удаляет S3-объект с повтором при временной ошибке. Заметки этим заданием не затрагиваются.
- Защита от злоупотреблений включает общий и отдельный upload rate limit, максимум 20 загрузок в час на участника, квоту 500 МБ активных фотографий на кабинет и серверные проверки количества, типа и размера.
- Только преподаватель может загружать PDF, DOC, DOCX и изображения в библиотеку кабинета. Один файл ограничен 25 МБ, кабинет — 50 успешными загрузками за календарный месяц и 5 ГБ активных материалов. Изображения декодируются сервером, уменьшаются и сохраняются как WebP без исходника и EXIF. SHA-256 не позволяет хранить вторую активную копию того же файла в одном кабинете.
- Материал хранится в отдельном закрытом S3-префиксе один раз и связывается с любым числом уроков через `lesson_resource_links` либо напрямую с учениками через `student_resource_links`. Обе связи открывают доступ к тому же S3-объекту без создания копии; постоянных публичных URL и просмотра без сессии нет.
- Раздел материалов ученика агрегирует без копирования все файлы библиотеки, связанные с его уроками или выданные ему напрямую, и ещё не удалённые фотографии преподавателя. Просмотр PDF, DOCX и изображений проходит внутри кабинета через те же защищённые API с повторной проверкой сессии, `workspace_id` и связи с конкретным учеником; скачивание остаётся отдельным действием.
- Материалы библиотеки не удаляются по сроку. Удаление из библиотеки сразу убирает связи с уроками и прямые назначения ученикам, затем переводит объект в очередь worker для удаления из S3. Загрузка и выдача нового доступа требуют актуального принятия `content_rules` редакции 1.2; закрыть уже выданный доступ можно независимо от принятия новой редакции правил.
- Материал может иметь одну папку и до десяти тегов длиной до 30 символов. Поиск и фильтры работают только внутри текущего `workspace_id`; списки назначений строятся из действительных связей `lesson_resource_links` и `student_resource_links` и не принимаются от клиента.
- Замена файла сохраняет `teacher_resources.id`, поэтому все связи с уроками остаются действительными. Новый S3-объект загружается до атомарного переключения записи, каждая версия учитывается в месячном лимите через `teacher_resource_upload_events`, а прежний объект попадает в `teacher_resource_file_cleanup` и удаляется worker с повтором после временной ошибки.
- `last_used_at` обновляется при назначении материала уроку и при успешном скачивании. Он используется только для сортировки «Недавно использованные» и не даёт дополнительных прав доступа.
- Домашнее задание хранится отдельно от заметок: преподаватель редактирует поле задания, ученик — собственный ответ или комментарий. Оба поля ограничены 4000 символами, видны обоим участникам урока и не удаляются автоматически. Документы и фотографии повторно не загружаются специально для домашнего задания, а используются из материалов того же урока.

## Сообщения и оформление профиля

- Личные сообщения разрешены только между активным учеником с подключённым аккаунтом и активным `owner` или `teacher` того же `workspace_id`. Идентификатор собеседника из клиента всегда повторно проверяется сервером.
- Сообщение содержит только текст от 1 до 500 символов. Вложения не поддерживаются; действует общий минутный rate limit и дополнительный предел 60 сообщений от участника за час.
- Прочитанность фиксируется только получателем. Сообщения не создают Telegram-доставку: Telegram остаётся каналом расписания и запросов, а переписка читается внутри кабинета.
- Участник выбирает цвет своего аватара из серверного закрытого списка. Преподаватель может сохранить отдельный цвет карточки ученика только для собственного отображения; выбор ученика при этом не меняется.
- Фото профиля ограничено 2 МБ, требует принятия актуальных правил контента, декодируется сервером, обрезается до 512×512 и сохраняется как WebP без исходного файла и EXIF в отдельном закрытом S3-префиксе. Доступ к файлу возможен только участникам того же кабинета через API с сессией.
- Фото профиля хранится до замены, явного удаления или окончательного удаления карточки. Оно не подпадает под 90-дневный срок фотографий урока.

- Название роли преподавателя хранится в профиле отдельно от имени, может быть пустым и ограничено 50 символами.
- Ученика можно создать без фамилии, email и аккаунта. Для внутреннего учёта обязательно только имя.
- Email нужен только для подключения личного кабинета. Приглашение нельзя создать без email.
- Приглашение одноразовое, действует 14 дней, а в PostgreSQL хранится только SHA-256-хеш токена.
- Выпуск нового приглашения делает предыдущие непринятые приглашения этого ученика недействительными.
- Если локальная учётная запись с email приглашения уже существует, её можно подключить к новой карточке только после успешной проверки прежнего пароля; приглашение не сбрасывает пароль существующего аккаунта.
- Восстановление пароля отправляет одноразовую ссылку через SMTP и всегда показывает одинаковый ответ независимо от наличия аккаунта. Новый пароль принимается только вместе с действующим токеном из этой ссылки.
- Рабочая ссылка восстановления всегда возвращает на `PUBLIC_APP_URL`; токен действует один час, хранится только как SHA-256-хеш, погашается после использования и отзывает прежние активные сессии.
- После подключения аккаунта email ученика нельзя произвольно заменить из обычной формы: он связан с учётной записью авторизации.
- Архивация ученика выключает его постоянные серии, отменяет будущие уроки без списания и закрывает ожидающие запросы, но сохраняет карточку, баланс и историю. Восстановление возвращает карточку без автоматического возобновления прежнего расписания.
- Безвозвратное удаление доступно только из архива и требует отдельного явного подтверждения. Оно удаляет связанные предметные данные ученика; общая локальная учётная запись удаляется только когда это безопасно для остальных связей пользователя.

## Расписание и уроки

- Постоянное расписание хранится в `lesson_series`; конкретные занятия всегда хранятся отдельными строками в `lessons`.
- Уроки постоянной серии создаются на 90 дней вперёд. Частичный уникальный индекс `(series_id, starts_at)` запрещает два активных урока одной серии, но позволяет хранить отменённый урок в истории.
- Плавающее расписание не имеет обязательного недельного шаблона; каждый урок создаётся отдельно или подтверждается из запроса ученика.
- В одном `workspace` два активных урока не могут пересекаться по времени. Проверка пересечения выполняется сервером перед созданием и переносом.
- Двойной урок — два обычных последовательных урока, связанные общим `group_id`. Они создаются, переносятся и отменяются одной операцией, но после проведения создают два независимых списания по одному занятию каждое.
- Своевременный запрос отмены одной из частей блокирует списание всей связанной пары. Если запроса нет, после завершения обеих частей с баланса суммарно списываются два занятия.
- «Удаление» урока является мягкой отменой: `status = cancelled`, `charge_status = waived`. Исторические записи физически не удаляются.
- Перенос отдельного урока меняет его время. Перенос урока постоянной серии отменяет исходный экземпляр и создаёт отдельный урок на новое время, не меняя недельный шаблон серии.
- Остановка серии деактивирует шаблон и отменяет только будущие активные уроки этой серии без списания.
- Каждое назначение, завершение, ручная отмена и перенос сохраняются неизменяемой записью в `lesson_events`. Для переноса фиксируются прежнее и новое время; журнал не заменяет текущее состояние урока в `lessons`.
- Пробное занятие можно назначить новому посетителю без создания видимой карточки ученика. Такой посетитель хранится как скрытый `member` с `is_trial_contact = 1`, а преобразование в ученика снимает этот флаг и сохраняет урок и его историю.
- Существующему ученику пробное занятие разрешено только пока у него нет завершённых обычных занятий и записей оплаты. После появления платной истории сервер отклоняет пробное занятие независимо от интерфейса.

## Запросы ученика

- Ученик не меняет расписание напрямую: создаётся `lesson_request` со статусом `pending`, решение принимает преподаватель.
- Возможные типы: `cancel`, `reschedule`, `new_lesson`; новый урок может предлагать только ученик с плавающим расписанием.
- Для одного урока может ожидать решения только один запрос: отмену и перенос нельзя отправить одновременно. После подтверждения одного запроса остальные ожидающие запросы по связанному уроку становятся неактуальными.
- Cloudflare ограничивает общий поток изменений одной сессии 60 запросами в минуту, а создание запросов учеником — 10 запросами в минуту на `member`. Превышение возвращает `429` и не выполняет предметную запись.
- Ожидающие запросы дополнительно защищены частичными уникальными индексами D1, поэтому параллельные обращения также не создают дубликаты.
- Отмену можно запросить до 23:59:59.999 предыдущего календарного дня по часовому поясу кабинета (сейчас `Europe/Moscow`).
- Своевременный ожидающий запрос отмены блокирует автоматическое списание, даже если преподаватель ещё не ответил.
- Подтверждение или отклонение запроса сохраняет решение, автора и время решения и создаёт уведомление ученику.
- Рабочие интервалы преподаватель настраивает сам; поддерживаются несколько интервалов в день и переход через полночь.
- Свободные слоты видит только ученик с персонально включённым доступом. Сервер возвращает ему только свободное время без данных других учеников.
- Выбор свободного слота создаёт обычный запрос `new_lesson`, а не бронирует время. Для ученика с постоянным расписанием сервер дополнительно проверяет, что выбранный слот всё ещё свободен и входит в рабочие часы.

## Баланс и автоматическое списание

- Баланс не редактируется одним числом. Он равен сумме неизменяемых операций `balance_entries`.
- Оплата добавляет положительное количество занятий; проведённый урок создаёт `lesson_charge = -1`; отрицательный итоговый баланс допустим.
- Ошибочная оплата не удаляется и не переносится другому ученику. Для неё создаётся связанная операция `refund` с противоположным количеством занятий; исходная запись остаётся в истории.
- Начальный долг и другие ручные исправления оформляются отдельной операцией `adjustment` с обязательной причиной; существующие записи уроков и оплат при этом не изменяются.
- `reverses_entry_id` связывает отмену с исходной оплатой, а частичный уникальный индекс запрещает отменить одну оплату дважды, в том числе при параллельных запросах.
- После `ends_at` активный урок считается проведённым, даже если ученик не пришёл.
- Списание создаётся ровно один раз. Уникальность `(lesson_id, kind)` и `INSERT OR IGNORE` защищают от повторного списания при параллельных или повторных запусках.
- Отменённый урок и урок со своевременным ожидающим запросом отмены не списываются.
- Обработка запускается при обращении к API и фоновым Worker cron каждые 15 минут; обе ветки используют одну функцию `settlePastLessons`.
- Бесплатное пробное занятие хранится как `lessons.lesson_type = 'trial'`. Оно создаётся только разово на один час; после завершения получает `charge_status = 'waived'` и не создаёт запись списания в `balance_entries`.

## Целостность операций

- Связанные изменения выполняются одним `db.batch`: например, изменение урока, решение запроса и уведомление.
- Перед записью сервер повторно проверяет роль, `workspace_id`, существование сущности, статус, диапазон дат и конфликт времени.
- JSON-тело ограничено 16 КБ, принимает только известные поля, а комментарий ученика ограничен 500 символами.
- Уведомление не заменяет предметную запись: источником истины остаются урок, запрос или операция баланса.
- Уведомление хранит ссылки на связанного ученика и, когда применимо, запрос, урок или операцию баланса. Интерфейс получает полные детали из этих предметных записей, поэтому не полагается на общий текст уведомления.
- Открытие источника уведомления помечает прочитанной только выбранную запись. Серверный `UPDATE` всегда ограничивается одновременно идентификатором уведомления и получателя; массовая отметка всех уведомлений является отдельным явным действием.
- Уведомление об уже подтверждённом или отклонённом запросе не должно отображаться как актуальный ожидающий запрос. Счётчик событий не суммирует одну и ту же заявку одновременно как запрос и как непрочитанное уведомление.
- `data_changes` — адресный журнал синхронизации, а не источник предметных данных. Триггеры D1 записывают получателя и названия изменившихся разделов в той же транзакции, что и основное изменение.
- Фоновая проверка по курсору читает только журнал. Если изменений нет, предметные таблицы не запрашиваются; если они есть, API возвращает только затронутые разделы и по-прежнему применяет обычное ограничение по `workspace_id` и ученику.
- Клиент проверяет курсор каждые 30 секунд только в видимой вкладке и каждые 5 минут в скрытой, а также сразу после возврата фокуса или восстановления сети. Этот интервал не отменяет серверные ограничения доступа и не должен заменяться полной загрузкой кабинета на каждом тике.
- В Node-контуре PostgreSQL `LISTEN/NOTIFY` будит адресный SSE-канал открытого кабинета сразу после фиксации `data_changes`. Периодическая проверка по курсору сохраняется как страховка после разрыва соединения и не заменяется отдельным источником предметных данных.
- Исправления не должны физически удалять рабочие данные без явного решения пользователя и предварительной проверки связей.

## Групповые занятия

- Группа — постоянная сущность кабинета (хор, ансамбль): `student_groups` (название, `members_visible`, `status` active/archived), состав `student_group_members`, недельные слоты `student_group_slots` (день, начало, длительность). Миграция `0015_student_groups.sql`.
- Занятие группы хранится **отдельной строкой `lessons` на каждого участника** с общим `class_id` (и `class_slot_id`, если оно создано по слоту). Так баланс, списание, отмена и история работают для каждого ученика как у обычного урока: за проведённое занятие у каждого участника списывается одно занятие по его цене.
- Ограничение «уроки кабинета не пересекаются» стало `EXCLUDE ... (COALESCE(class_id, id) WITH <>)`: строки одной группы могут совпадать по времени, с любыми другими уроками — нет. Уникальный индекс `(class_slot_id, student_id, starts_at)` не даёт задвоить занятие по слоту.
- Занятия по слотам генерирует `ensureSeriesLessons` (`lib/app-data/route-utils.ts`) на те же 90 дней. Новому участнику достаются только занятия, которые у группы ещё идут: занятие, отменённое для всех, ему не создаётся. Дополнительные и перенесённые занятия (без `class_slot_id`) копируются новому участнику при добавлении в состав и при создании ученика сразу в группе (`manualSessionCopies`).
- Отмена для одного участника — обычная мягкая отмена его строки (`deleteLesson`); остальные не затрагиваются. «Отменить для всех» (`cancelGroupSession`) и «Перенести для всех» (`rescheduleGroupSession`) работают со всеми строками занятия одной транзакцией; перенос проверяет пересечение с чужими уроками.
- Удаление участника из состава отменяет его будущие занятия группы без списания и отвязывает их от слота (`class_slot_id = NULL`), чтобы при повторном добавлении генератор создал новые строки. Изменение расписания отменяет будущие занятия по старым слотам и создаёт новые. Архив группы отменяет все её будущие занятия.
- Действия: `createGroup`, `updateGroup`, `setGroupMembers`, `setGroupSlots`, `archiveGroup`, `addGroupSession`, `cancelGroupSession`, `rescheduleGroupSession` (`lib/app-data/write-group-actions.ts`); `createStudent` принимает `groupId`.
- Чтение: у уроков есть `classId` и `className`; преподаватель получает `groups` и `groupAbsences` — отменённые строки текущих участников на будущих занятиях, которые у группы ещё идут и которые этот ученик не получил снова. Интерфейс склеивает строки в одну карточку (`lib/group-sessions.ts`).
- Кабинет ученика: у своих уроков ученик видит `classId` и `className`, а в `myGroups` — свои активные группы; имена остальных участников (`classmates`, включая ещё не принявших приглашение) приходят только при `members_visible`. Данные групп преподавателя (`groups`, `groupAbsences`) ученику не отдаются.
- «Не приду»: `submitStudentRequest` с `requestType: "cancel"` по уроку группы не создаёт запрос, а сразу отменяет только строку этого ученика без списания (тот же срок — до 23:59 предыдущего дня), пишет `lesson_events` и уведомление преподавателю `lesson_cancelled` «Ученик не придёт» (уходит и в Telegram по настройке «расписание»). Ответ содержит `cancelled: true`. Перенос урока группы учеником сервер отклоняет (409): переносит преподаватель.
- Ещё не сделано (шаг 3): материалы к групповому занятию не раздаются всем участникам (кнопка «Материалы» у группового занятия скрыта); статистика считает занятие по строкам участников; напоминания и сводка преподавателю идут по каждой строке.

## Стоимость занятий

- Цены необязательны и задаются у ученика: `members.lesson_price_cents`, `double_lesson_price_cents` (двойной урок; пусто — как два обычных), `trial_lesson_price_cents` (пусто — пробное бесплатно) и `price_currency` — свободная подпись валюты до 12 символов. Все суммы — целые числа в сотых долях (копейки, центы).
- Сумма запоминается в самой операции баланса (`balance_entries.amount_cents`): у оплаты — введённая или посчитанная по цене ученика, у списания за урок — цена на момент списания; двойной урок делит свою цену между двумя частями. Изменение цены не переписывает прошлые операции.
- Цены и суммы — рабочие данные преподавателя: API не отдаёт их в кабинет ученика.
- Статистика: `GET /api/teacher-stats?from&to` (только owner/teacher, период до 400 дней, даты в часовом поясе кабинета) считает показатели на сервере в `lib/teacher-stats.ts`; двойной урок — один урок. «Должны сейчас» — текущий срез балансов, остальное — за период; «приостановили» — остановленные постоянные расписания (`series_stopped`).

## Внешние уведомления

- Внутреннее уведомление или предметная запись создаются независимо от доступности внешнего сервиса. Сетевой запрос к Telegram нельзя выполнять внутри операции изменения урока или запроса ученика.
- Если production-сервер не достигает Telegram, используется только аутентифицированный relay из `workers/telegram-relay/`. Его список методов закрыт; Telegram bot token хранится как Cloudflare secret, relay-secret — отдельно на relay и VPS.
- PostgreSQL-триггер `notifications_enqueue_telegram` атомарно создаёт `telegram_deliveries` только для подключённых участников, разрешённых типов и включённых персональных категорий: расписание и запросы, новые сообщения, материалы и домашние задания. Текст личного сообщения и содержимое закрытого файла в Telegram не отправляются.
- Напоминание создаёт Node worker, когда до начала урока остаётся не более 24 часов. Ученик получает одно персональное сообщение об уроке с датой, преподавателем и текущим балансом (сумма `balance_entries` на момент постановки напоминания; отрицательный показывается как «долг N занятий»), а owner — одно сводное расписание на календарный день со всеми оставшимися уроками этого дня. Связанный двойной урок показывается одной строкой; дневная сводка защищена от повторной отправки отдельным `dedupe_key`.
- `telegram_deliveries.dedupe_key` обязателен и уникален. Повторный worker или повторная предметная операция не должны создавать вторую доставку одного события.
- `notification_preferences` принадлежит конкретному `member`: звук в открытом кабинете и каждая категория Telegram настраиваются независимо. Для прежних пользователей расписание и напоминания остаются включены по умолчанию, а новые категории Telegram требуют явного включения.
- Worker забирает только наступившие `pending`-записи, возвращает зависшие `sending` старше десяти минут, повторяет временные ошибки не более пяти раз и не журналирует текст сообщения или `chat_id`.
- Ответ Telegram `403` считается постоянным отказом: связь отключается, доставка отменяется. Временная недоступность не влияет на сохранение расписания.
- Webhook принимает только запросы с точным `X-Telegram-Bot-Api-Secret-Token`, только приватную команду `/start` и действующий одноразовый токен. Токен действует 15 минут и хранится только как SHA-256-хеш.
- Отключение Telegram инвалидирует непринятые токены и отменяет ожидающие доставки. Это не удаляет внутренние уведомления и предметные данные.

## Схема и миграции

- Рабочая схема описывается в `db/postgres/schema.ts`; каждое production-изменение получает новый проверенный вручную файл в `drizzle-postgres/`.
- `db/schema.ts` и `drizzle/` относятся к совместимому D1-контуру. Уже применённые D1-миграции не редактируются.
- Перед рабочей миграцией нужно проверить список ожидающих миграций и возможные конфликты данных. После неё выполняется одна производственная сборка и публикация.
- `.env.local`, локальная D1, `dist/` и `.wrangler/` не коммитятся.
- PostgreSQL-миграции являются добавочными и не переписываются после применения. Финальный импорт D1 выполняется только во время согласованного окна записи, повторяемым скриптом, затем проверяется по количествам, связям, контрольным суммам и ключевым бизнес-инвариантам.
- `scripts/import-d1-sqlite-to-postgres.mjs` работает только с пустыми предметными таблицами. `scripts/merge-d1-sqlite-into-postgres.mjs` был использован для одноразового объединения с непустым production: по умолчанию он выполняет транзакционный dry-run и откат, а запись требует явного `--apply`. Production merge уже завершён, поэтому повторный запуск с `--apply` запрещён без нового backup, dry-run и отдельного решения владельца.
- В Node-контуре `db/postgres-d1.ts` является временным совместимым слоем для существующей серверной бизнес-логики. Все placeholder-ы остаются параметризованными, D1 `batch` соответствует одной PostgreSQL-транзакции, а ошибки уникальности и пересечения переводятся в прежние безопасные ответы API.
